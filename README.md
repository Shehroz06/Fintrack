# FinTrack

A full-stack personal finance tracker. Track income and expenses, set a monthly budget, watch progress toward savings goals, and get simple insights and AI-assisted recommendations about your spending — all scoped to your own JWT-authenticated account.

---

## Features

- **Authentication** — Register/login with email + password (bcrypt, 12 rounds). Sessions are signed JWTs stored in `localStorage`. Every API route below `/api/*` (except `/api/auth/*` and `/api/health`) requires a valid token, and every query is scoped to the authenticated user — one account can never read or modify another's data (see [Testing](#testing)).
- **Transactions** — Add, edit, delete, list, search, and filter (by type/category/free text, client-side over the loaded set) income/expense/investment/savings entries. Category is a free-text field with a suggestion list, so you can use the predefined categories or type your own. CSV export of your full history.
- **Recurring transactions** — Schedule a transaction to repeat daily or monthly (salary, rent, subscriptions). Occurrences are materialized lazily whenever you load your transactions, catching up on any periods missed since your last visit rather than skipping them.
- **Monthly budget** — Set one overall budget per calendar month; see amount spent, remaining, and percentage used, with a healthy/near-limit/exceeded status computed server-side (not hardcoded thresholds in the UI).
- **Financial goals** — Target amount, deadline, progress %, remaining amount, days left.
- **Insights** — Three plain-language facts computed from your own transaction data: this month's savings, month-over-month expense change, and your top spending category.
- **AI recommendations (optional)** — If `GEMINI_API_KEY` is set, both transaction categorization (as a fallback when keyword rules find no match) and the "Smart Insights" tips are generated by Gemini, with automatic fallback to a local rule-based engine if the API is unconfigured, rate-limited, or errors.
- **Reports** — Monthly income/expenses/invested trend, spending-by-category breakdown (filterable by This Month / Last Month / This Year / All Time), goal progress.

## Architecture

Layering is: **routes** (`server.js`) → **services** (`Services.js`, one class per domain: transactions, goals, recurring rules, budgets) → **DatabaseSingleton** (parameterized MySQL queries). Routes handle HTTP concerns (validation, status codes) and delegate all persistence/business logic to services — no raw SQL in `server.js` outside of small one-off lookups (e.g. resolving a user's default account id).

### Design patterns actually in use

| Pattern | Where | Why it's there |
|---|---|---|
| Singleton | `DatabaseSingleton.js` | One MySQL connection pool shared across the app. |
| State | `FinancialState.js` | Budgeting / Savings / Investment modes each generate different recommendation text from the same transaction data — swapping `context.setState(...)` changes behavior without branching logic scattered through the code. |
| Service Layer | `Services.js` | Each class (`TransactionService`, `GoalTrackerService`, `RecurringTransactionService`, `BudgetService`) owns one domain's persistence and rules, independent of Express. |

Two previously present patterns — a Strategy-pattern budgeting calculator and a Composite-pattern account hierarchy — were removed during this pass. Both were fully implemented but **orphaned**: the calculator's frontend component was never imported anywhere in the app, and the composite account manager was instantiated in `server.js` but never actually called (the live `/api/portfolio` routes queried the database directly instead). Keeping unreachable code around to demonstrate a pattern name isn't good architecture, so they were deleted in favor of the persistent Monthly Budget feature that's actually wired end to end. This is a judgment call worth being upfront about if it comes up in review.

### SOLID, concretely

- **S** — `TransactionService`, `GoalTrackerService`, `RecurringTransactionService`, and `BudgetService` each own exactly one table's rules; `RecommendationEngine` only produces recommendations, `GeminiService` only talks to the Gemini API.
- **O** — `RecommendationEngine.generateRecommendations()` tries Gemini and falls back to the local rule engine without either code path knowing about the other; adding a third provider wouldn't require touching existing branches.
- **L** — Any `FinancialState` subclass (`BudgetingState`, `SavingsState`, `InvestmentState`) can stand in for the base class in `FinancialStateManager` — same interface, all substitutable.
- **I** — The frontend `api.js` client exposes one narrow method per endpoint rather than a single generic `request()` callers have to shape themselves.
- **D** — Routes depend on service instances, not on `mysql2` or table names directly; swapping the storage layer would only touch `Services.js`.

## Database

MySQL, 6 tables. All monetary columns are `DECIMAL(15,2)` (never floating point). All user-owned tables have `user_id` with `FOREIGN KEY ... ON DELETE CASCADE`, and every service method scopes its query with `WHERE user_id = ?` — the authorization boundary is enforced at the data layer, not just in route handlers.

```
users ──┬── accounts ──┬── transactions
        ├── financial_goals
        ├── recurring_transactions
        ├── budgets  (UNIQUE user_id + month)
        └── user_settings
```

Indexes: `transactions(user_id)`, `transactions(transaction_date)`, `transactions(type)`, `recurring_transactions(next_run_date)` — the columns actually used in `WHERE`/filter clauses. `budgets` has a `UNIQUE(user_id, month)` constraint so "set this month's budget" is a single `INSERT ... ON DUPLICATE KEY UPDATE`, not a read-then-write race.

## Setup

### Prerequisites

- Node.js 18+
- MySQL 8+

### 1. Database

```bash
mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS finance_management;"
mysql -u root -p finance_management < backend/database_schema.sql
```

### 2. Backend

```bash
cd backend
npm install
cp .env.example .env
# Edit .env — set DB_PASSWORD and a strong JWT_SECRET (the server refuses to
# start without one — see Security below)
npm start
# Runs on http://localhost:5000
```

### 3. Frontend

```bash
cd frontend
npm install
npm start
# Opens at http://localhost:3000
```

### 4. Run both at once

```bash
./run.sh
```

Installs dependencies on first run if missing, prompts you to fill in `backend/.env` if it doesn't exist yet, and starts both servers (`Ctrl+C` stops both).

### 5. Tests

```bash
cd backend
npm test
```

## Environment Variables

Copy `backend/.env.example` to `backend/.env`:

| Variable | Description |
|----------|-------------|
| `DB_HOST` | MySQL host (default: localhost) |
| `DB_USER` | MySQL user |
| `DB_PASSWORD` | MySQL password |
| `DB_NAME` | Database name (finance_management) |
| `PORT` | Backend port (default: 5000) |
| `JWT_SECRET` | Secret for signing JWTs. **Required** — the server exits at startup if this is missing rather than silently falling back to a known default. |
| `JWT_EXPIRES_IN` | Token lifetime (default: 7d) |
| `FRONTEND_URL` | Allowed CORS origin (default: http://localhost:3000) |
| `GEMINI_API_KEY` | Optional. Enables Gemini-powered recommendations and transaction categorization. |
| `GEMINI_MODEL` | Gemini model id (default: gemini-2.0-flash) |

## Security

- Passwords hashed with bcrypt (12 rounds); never logged or returned by any endpoint.
- JWTs signed with a required secret — no insecure default fallback (previously present, fixed during this audit; see below).
- Every service method takes the authenticated `userId` from the verified JWT and scopes its query with it — confirmed by `authorization.test.js`, which registers two real accounts and asserts one can't read, edit, or delete the other's transactions, goals, or budget via id-guessing.
- All SQL uses parameterized queries (`mysql2` placeholders) — no string-built SQL anywhere.
- CORS restricted to `FRONTEND_URL`, not wildcard.
- A small in-memory rate limiter caps `/api/auth/*` at 10 requests per IP per 15 minutes, to blunt brute-force login/register attempts without adding a new dependency.
- `.env` is gitignored and never committed.

**Fixed during this audit:** `JWT_SECRET` previously had a hardcoded fallback string (`'fintrack-dev-secret-change-in-production'`) in two files. If the env var was ever unset — a misconfigured deploy, a copy-pasted `.env` missing a line — every token would silently be signed with a secret visible in the source code, making them trivially forgeable. The server now refuses to start at all if `JWT_SECRET` isn't set.

**Known limitation:** the rate limiter is a single in-memory `Map`, fine for a single-process app like this but not shared across multiple server instances. Not fixed here since it would mean adding Redis or similar for a problem this project doesn't have yet.

## Testing

```
Test Suites: 3 passed, 3 total
Tests:       53 passed, 53 total
```

- `RecommendationEngine.test.js` — pure unit tests for the local rule-based recommendation/categorization engine (pre-existing).
- `budget.test.js` — pure unit tests for `calculateBudgetUsage()`: healthy/near-limit/exceeded thresholds, the exact-100% boundary, division-by-zero safety, invalid input.
- `authorization.test.js` — integration tests against the real Express app (`supertest`) and a real (throwaway, self-cleaning) database record: registers two users, then asserts User B cannot see, edit, or delete User A's transactions, goals, or budget by guessing ids — the single most important property for a multi-tenant finance app.

`server.js` only calls `app.listen()` when run directly (`node server.js`) — a `require.main === module` guard — so `authorization.test.js` can `require()` the app and drive it with supertest without a real network listener or port conflicts.

## Future Improvements

- Per-category budgets (currently one overall monthly budget by design, to keep the feature simple and predictable).
